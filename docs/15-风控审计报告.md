## C 节：4 条新需求 vs 现状 Gap 矩阵

### R1：单商户日交易额 > 50 万美元 自动熔断 30 分钟

**现有最接近**：
- `t_channel_account.daily_limit_amount` 已有（但是**通道账号级**，不是商户级）
- `CircuitBreakerEngine` 已能执行熔断（按通道 / 商户）
- `t_mch_info.auto_suspend_threshold` 已有（但是**评分维度**的，不是金额维度）

| 维度 | 差什么 |
|---|---|
| **DB schema** | ① `t_risk_threshold_config` 新增 3 个 KV：`merchant.daily_amount.threshold_usd`、`merchant.daily_amount.circuit_seconds`、`merchant.daily_amount.enabled`（全局默认）<br>② 可选：`t_mch_info` 加 `daily_amount_threshold_usd` / `daily_amount_circuit_seconds` 两列（商户级覆盖，参考既有 `chargeback_alert_threshold` 模式） |
| **Service** | ① 新增 `MerchantDailyAmountGuard`（监听支付成功事件，按商户累计当日 USD 折算金额，过阈触发 `CircuitBreakerEngine#trip(merchantNo, 1800s)`）<br>② 累计存 Redis `key=mch:daily_amount:{mchNo}:{yyyyMMdd}` TTL 36h |
| **前端** | `jeepay-ui-manager` 的"风险阈值配置"页加 3 个全局项；商户管理页加"日额熔断"两项（默认空=用全局） |
| **调度** | 不需要（实时事件驱动），但建议加一个 0 点 Redis key 兜底清理 |

**优先级 P0**　**估时 1.5 人天**

---

### R2：PayPal 拒付率 > 1% 时降低该商户的 Stripe 通道权重

**现有最接近**：
- `t_channel_health_snapshot.chargeback_rate`（30 天滚动）已有 → 数据源 ✓
- `ChannelRouterService` 选路时使用 `t_channel_account.weight` —— 是商户**无关**的全局权重
- 现状**没有**"商户 × 通道"维度的权重表，**这是最大 gap**

| 维度 | 差什么 |
|---|---|
| **DB schema** | ① 新增 `t_merchant_channel_weight_override`（mch_no / if_code / weight_delta / reason / expire_at），唯一索引 `(mch_no, if_code)`<br>② `t_risk_threshold_config` 加 KV：`r2.paypal_chargeback.threshold`(=1.0) / `r2.observe_window_days`(=30) / `r2.target_channel`(=stripe) / `r2.weight_delta`(=-30) / `r2.enabled` / `r2.recover_window_days`(=7 连续低于阈值自动恢复) |
| **Service** | ① 新增 `CrossChannelPenaltyService.evaluate()`：扫每个商户的 PayPal 拒付率，超阈则写 override（也支持自动恢复）<br>② `ChannelRouterService` 选路加权阶段读 override 表，对目标通道做 `weight + weight_delta`（地板 0） |
| **前端** | 配置页加规则编辑；商户详情加"通道权重 override"只读列表 |
| **调度** | 新增 `CrossChannelPenaltySchedule`（每小时跑一次 `evaluate()`） |

**优先级 P1**　**估时 3 人天**（最重，因为多了一张表 + 改路由器）

---

### R3：Stripe Radar `early_fraud_warning` → 30 分钟内冻结该卡 BIN

**现有最接近**：
- `t_risk_blacklist.list_type='card_bin'` 已支持，`expire_at` 字段已有 → 表结构 ✓
- 现状**没有** Stripe webhook 接收 `radar.early_fraud_warning` 的入口（搜 `jeepay-payment` 没有相应 handler）

| 维度 | 差什么 |
|---|---|
| **DB schema** | `t_risk_threshold_config` 新增：`r3.efw_freeze_minutes`(=30) / `r3.enabled` / `r3.notify_alert`(=true 联动 RiskAlertNotifier) |
| **Service** | ① 在 `jeepay-payment` 的 `channel/stripe/` 下扩展 webhook 路由（找到现有 `StripeWebhookXxx` 类追加 case `radar.early_fraud_warning`，如不存在则新建 `StripeRadarWebhookHandler`）<br>② 从 payload 取 `charge.payment_method_details.card.fingerprint` 或 `card.last4`+BIN，先调 Stripe API 取 BIN（前 6 位）<br>③ 调 `RiskBlacklistService.add(list_type='card_bin', value=bin, expire_at=now+30min, source='auto', reason='stripe_efw:'+chargeId)`<br>④ 触发 `RiskAlertNotifier`（Telegram + Email） |
| **前端** | 黑名单页过滤维度加 source=stripe_efw；规则配置页加 r3.* |
| **调度** | 不需要（webhook 推） |

**优先级 P0**　**估时 2 人天**（webhook 签名校验 + Stripe API 调用是新增依赖）

**⚠️ 安全提示**：必须在 webhook handler 入口校验 `Stripe-Signature` 头，否则恶意构造可任意冻结卡。

### R4：黑名单扩展——邮箱后缀 / 设备指纹 / 邮箱后缀+指纹组合

**现有最接近**：
- `t_risk_blacklist.list_type` 已支持 `email` 和 `device` → 单维度 ✓
- 现状指纹采集**完全没有**（`docs/FINGERPRINT_POC.md` 仅 POC 文档，未落地代码）
- 现状无"组合规则"语义（邮箱后缀 AND 指纹 联合命中）

| 子项 | 差什么 |
|---|---|
| **R4a 邮箱后缀通配**　P0　0.5 人天 | DB：无需改表（用 `list_type='email'` + `list_value='*@temp-mail.org'`）；Service：`RiskBlacklistService.matchEmail()` 加通配匹配（`startsWith('*@')` 则比对后缀） |
| **R4b 设备指纹采集 + 黑名单**　P1　4 人天 | 前端（收银台）：集成 FingerprintJS / ClientJS，下单时把 visitorId 放在 `body.deviceFingerprint`；后端 DTO 加字段、写入 `t_pay_order` 新列 `device_fingerprint`（这是新列！）；`OrderRiskHookService` pre-check 时读 `t_risk_blacklist (list_type='device')` 比对 |
| **R4c 组合规则**　P2　2 人天 | DB：新增 `t_risk_blacklist_combo` (id, rule_name, conditions JSON, state)；Service：`OrderRiskHookService` 拼 pre-check 链路，每个 combo 规则单独命中 |

**模块总估时 P0+P1 = 4.5 人天**（P2 看运营是否真要"组合"，可推迟）
