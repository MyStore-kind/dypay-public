## 二、Step-by-Step 上线前自检

### Step 0：本地静态校验（已完成 ✅）

- 6 个新/改 Java 文件的 import / 方法签名 / 字段引用静态扫过一遍，全通过。
- 风险点：本地无 mvn，无法跑真实编译；服务器侧首跑 `mvn package` 仍可能因 Lombok / SpringDoc 等环境差异报错。

### Step 1：服务器端首次编译

```bash
# 在服务器 dypay 目录
mvn -DskipTests -pl jeepay-core,jeepay-service,jeepay-payment,jeepay-manager,jeepay-merchant -am clean package
```

**预期产物**：
- `jeepay-payment/target/jeepay-payment-Final.jar`
- `jeepay-manager/target/jeepay-manager-Final.jar`
- `jeepay-merchant/target/jeepay-merchant-Final.jar`

**最可能挂的地方（按概率排序）**：
1. ❗ `MerchantDailyAmountGuard` 引用了 `SpringBeansUtil.getBean(StringRedisTemplate.class)`——确认 `jeepay-core` 的 SpringBeansUtil 真支持泛型重载，不行就改成 `(StringRedisTemplate) SpringBeansUtil.getBean("stringRedisTemplate")` 字符串入参形式。
2. ❗ `Charge.PaymentMethodDetails.Card` 嵌套类路径若 Stripe SDK 升降版本可能变化，需要 `mvn dependency:tree -pl jeepay-payment | grep stripe-java` 看实际版本。
3. ❗ Lombok `@Data` + 新增字段——若全局禁了 Lombok 注解处理器会缺 getter。

### Step 2：`.env` 必填项校对

```bash
cd deploy && cp .env.example .env && vi .env
```

**本批次新增/必改项**：

| 变量 | 默认 fallback | 生产必改？ | 说明 |
|---|---|---|---|
| `JEEPAY_CORS_ORIGINS` | `http://localhost,...` | **是** | 不填生产前端访问会 CORS 拒；填错（空字符串）会让三端启动失败（fail-fast） |
| `JEEPAY_JWT_SECRET` | `CHANGE_ME_IN_PROD_OR_FAIL` | **是** | 三端共用 secret，必须 ≥64 字符随机串 |
| `DB_PASSWORD` / `MYSQL_ROOT_PASSWORD` | `CHANGE_ME_DB` | **是** | 已强制环境变量化 |
| `REDIS_PASSWORD` | `CHANGE_ME_REDIS` | **是** | docker-compose 启动会 `?REDIS_PASSWORD must be set` 强制要求 |
| `SPRINGDOC_ENABLED` | `false` | 保持 false | 生产严禁开 |
| `STRIPE_API_KEY` / `STRIPE_WEBHOOK_SECRET` | 测试值 | **是** | Stripe 通道必填 |
| `SMTP_*` | 空 | 可选 | R3 告警走邮件需要；否则只发 Telegram |
| `TELEGRAM_BOT_TOKEN` / `CHAT_ID` | 空 | 可选 | 同上 |
| `RISK_CONTROL_ENABLED` | true | 保持 | 总开关 |
| `RISK_GRAYSCALE` | 10 | 可调 | 测试期建议 10-30 |

### Step 3：SQL 补丁顺序（基于 docs/14 增量）

docs/14 已列出 11 个补丁的固定顺序。**本批次插入 1 个新文件**：

```bash
# 仅追加在已有顺序之后，已有顺序勿动
mysql -uroot -p dypaydb < sql/risk_v3_patch.sql   # ← 新增
```

幂等性：含 1 个 ALTER + 1 个 INSERT IGNORE。**二次执行 ALTER 会因列已存在报错** —— 二次部署时手工跳过 ALTER 段，仅执行 INSERT IGNORE。

### Step 4：首次部署后置脚本（安全加固）

```bash
# 4.1 生成新的 BCrypt 密文（在任一带 BCrypt 的环境执行）
htpasswd -nbBC 10 "" "你的新Admin密码" | tr -d ':\n' | sed 's/^\$2y/$2a/'
# 输出形如 $2a$10$XXXXXXXXXXXXXXX...

# 4.2 编辑 sql/post_install_hardening.sql
#     把 :NEW_BCRYPT_HASH 替换为上面的输出
#     把 :NEW_SALT 替换为 16-32 位随机字符串（openssl rand -hex 16）

# 4.3 执行（占位未替换会因 1/0 触发 ER_DIVIDE_BY_ZERO 中止脚本）
mysql -uroot -p dypaydb < sql/post_install_hardening.sql
```

**验证**：
```sql
SELECT salt FROM t_sys_user_auth WHERE user_id=801;
-- 应返回 ✅ 已强化（非 testkey）
```

### Step 6：阈值与告警通道 KV 初始化

`sql/risk_v3_patch.sql` 已默认 INSERT IGNORE 写入 R1/R3 阈值；运营如需调整，登录运营后台→`风险阈值配置`页面操作。

**重要的 5 个 KV 检查**（首次部署后用运营账号在前台或直接 SQL 看）：

```sql
SELECT config_key, config_value, action_enabled
FROM t_risk_threshold_config
WHERE config_key IN (
  'merchant.daily_amount.enabled',
  'merchant.daily_amount.threshold_usd',
  'stripe.efw.enabled',
  'stripe.efw.freeze_minutes',
  'notify.telegram.enabled'  -- 没配的话告警发不出去
);
```

期望：5 行全 `action_enabled=1`，threshold_usd=500000，freeze_minutes=30。

## 三、烟囱测试（部署完跑一遍）

### T1：基础登录

- 访问运营后台 → 用 `admin` + Step 4 的新密码登录 → 成功 → 立即创建独立账号并停用 admin

### T2：CORS 校验

- 浏览器 console 不报 "CORS blocked"
- `curl -i -H "Origin: https://攻击域名.com" https://你的域名/api/...` 应返回无 `Access-Control-Allow-Origin` 头

### T3：R1 日额熔断（手工触发）

- 临时把 `merchant.daily_amount.threshold_usd` 改成 `1`（USD）
- 用任一测试商户跑一笔 ≥1 USD 的成功支付
- 验证：
  - `redis-cli get mch:daily_amount:{mchNo}:{yyyymmdd}` ≥ 100（cent）
  - `redis-cli get risk:cb:mch:{mchNo}` 返回 JSON snapshot
  - `SELECT state FROM t_mch_info WHERE mch_no='测试商户'` = 0
  - 再下单时被拒（已熔断）
- 恢复：阈值改回 500000，`redis-cli del risk:cb:mch:{mchNo} risk:cb:reason:mch:{mchNo}`，UPDATE t_mch_info SET state=1。

### T4：R3 EFW 模拟

Stripe 测试模式不会主动发 EFW；可用 [Stripe CLI](https://stripe.com/docs/stripe-cli) `trigger radar.early_fraud_warning`：

```bash
stripe trigger radar.early_fraud_warning
```

验证：
- 日志含 `[StripeEFW] 冻结卡 BIN bin=xxxxxx ttlMin=30`
- `SELECT * FROM t_risk_blacklist WHERE source='stripe_efw'` 至少 1 行 + `expire_at > now()`
- Telegram / 邮件收到告警（如已配）

### T5：邮件告警链路

- 临时在运营后台触发任何一条风险告警（最简：直接 `INSERT INTO t_risk_alert_log` 然后看 RiskAlertNotifier 异步发出？）
- 或更直接：单测 `EmailChannel.send(RiskAlertType.SYSTEM, "test", "test")` 看真发出
- 看邮件标题：`type=SYSTEM` 时**不应带 "[风险告警] "** 前缀；其他类型应带

### T6：Telegram 超时验证（可选）

- 改 `/etc/hosts` 把 `api.telegram.org` 指到不可达 IP
- 触发任一告警
- 业务线程应在 8 秒内（3s 连接 + 5s 读）返回，不应吊死
