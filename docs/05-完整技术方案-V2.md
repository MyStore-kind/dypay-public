## 一、商业模式推断与技术架构定位

### 1.1 我推断的商业模式
```
跨境收单服务商（Cross-border PSP）
- 上游：聚合 Stripe / PayPal / Adyen 等国际通道
- 下游：服务跨境电商卖家、SaaS 出海企业
- 渠道：通过 3 级代理商分销
- 收入：手续费差 + 汇差 + 提现费
```

### 1.2 技术架构定位
**为什么选择 JeePay 作为主代码**：
| 维度 | JeePay 现状 | 是否满足国际四方 |
|------|-------------|------------------|
| 商户体系 | ✅ 支持普通商户 + 特约商户（ISV） | ⚠️ 缺代理商层级，已扩展 |
| 通道抽象 | ✅ `IPaymentService` 接口设计良好 | ✅ 易扩展 Stripe/PayPal |
| 订单系统 | ✅ 完整的下单/退款/分账流程 | ⚠️ 缺多币种，已扩展 |
| 分账能力 | ✅ 支持微信/支付宝分账 | ⚠️ 缺代理商分润，已扩展 |
| 安全性 | ✅ 接口签名、订单快照 | ✅ 满足 |
| 多币种 | ❌ 仅 CNY | ⚠️ 已通过 SQL 补丁扩展 |
| 国际通道 | ❌ 仅国内通道 | ✅ 已接入 Stripe |

**结论**：JeePay 80% 适合，剩 20% 通过扩展（而非重写）完成。

## 三、核心技术决策

### 3.1 关键决策表

| 决策项 | 方案 | 理由 |
|--------|------|------|
| **代码主体** | JeePay 100% 保留，扩展不重写 | 降低维护成本，便于跟进官方更新 |
| **金融精度** | 全程 `BigDecimal` | 避免 `double` 精度丢失 |
| **金额单位** | 统一存储"分"（最小货币单位） | 与 Stripe/JeePay 内部一致 |
| **币种标准** | ISO 4217（USD / EUR / JPY） | 国际标准 |
| **多币种存储** | 订单表加 `currency` 字段 | 不分表（运维简单） |
| **汇率快照** | 订单创建时记录 `exchange_rate` | 保证退款/对账一致性 |
| **代理商层级** | 最多 3 级（已实现） | 避免无限递归性能问题 |
| **分润触发** | 订单成功 Webhook 内同步触发 | 简单可靠，无需额外定时任务 |
| **Webhook 校验** | 通道方签名（如 Stripe-Signature） | 防伪造，必须用原始 payload |
| **数据库** | MySQL 8.0 主从 | JeePay 原生支持，社区成熟 |
| **缓存** | Redis（配置/汇率） | JeePay 已集成 |
| **消息队列** | RocketMQ（默认） | JeePay 已集成，支持事务消息 |

### 3.2 设计原则

1. **扩展而非重写**：不修改 JeePay 核心逻辑，所有新功能通过扩展接口实现
2. **币种感知**：所有金额相关代码必须携带币种上下文
3. **快照不可变**：订单一旦创建，币种/汇率/费率快照永不修改
4. **幂等设计**：所有 Webhook / 回调接口必须幂等
5. **失败可重试**：分润/结算失败可重试，不丢数据

## 六、订单流程改造

### 6.1 标准下单流程（多币种版）

```
1. 商户调用 /api/pay/unifiedOrder
   ├─ 必填：mchOrderNo, wayCode, amount, currency, subject
   └─ 可选：notifyUrl, returnUrl, divisionMode

2. 网关校验
   ├─ 商户/应用合法性
   ├─ 通道支持性（wayCode）
   └─ 【新增】币种合法性（CurrencyConfigService.validateAmount）

3. 创建订单
   ├─ 生成 payOrderId
   ├─ 【新增】记录订单币种 currency
   ├─ 【新增】查询并冻结汇率 exchange_rate
   ├─ 【新增】计算结算金额 settlement_amount
   └─ 状态：INIT

4. 路由到通道（Stripe）
   ├─ StripePaymentService.pay()
   ├─ 创建 PaymentIntent
   └─ 返回 client_secret 给前端

5. 用户完成支付
   └─ 前端 Stripe.js 收集卡信息

6. Stripe Webhook 通知
   ├─ /api/pay/notify/stripe
   ├─ 校验签名
   ├─ 更新订单为 SUCCESS
   ├─ 【新增】触发代理商分润（AgentProfitService.calculateAndRecordProfit）
   ├─ 触发商户分账（如配置）
   └─ 通知商户

7. 商户接收回调
   └─ /商户的 notifyUrl
```

### 6.2 退款流程（多币种版）

```
1. 商户调用 /api/pay/refundOrder
2. 校验原订单为 Stripe 通道
3. 创建退款单（沿用原订单汇率）
4. 调用 StripeRefundService.refund()
5. Stripe Webhook（charge.refunded）
6. 更新退款状态
7. 【新增】冻结对应代理商分润（state = FROZEN）
8. 通知商户
```

## 七、安全设计

### 7.1 安全分层

| 层级 | 措施 |
|------|------|
| 网络层 | HTTPS / TLS 1.2+，WAF |
| 应用层 | API 签名（HMAC-SHA256），幂等性校验 |
| 数据层 | 敏感字段加密（卡号永不存储） |
| 通道层 | Webhook 签名校验，IP 白名单 |
| 业务层 | 风控规则、限额、黑名单 |

### 7.2 PCI DSS 合规策略
- ✅ **不在后端接触卡号**：前端用 Stripe Elements 直接传到 Stripe
- ✅ **不存储卡号**：只存 PaymentIntent ID
- ✅ **使用 Stripe / PayPal 的 PCI 合规通道**：复用其合规资质

### 7.3 风控引擎（待实现，规划中）

```
单笔限额 → IP 频次 → 黑名单 → 设备指纹 → 行为评分 → 决策
```

## 八、合规与法律提示

### 8.1 必须解决的合规问题

| 问题 | 影响 | 建议 |
|------|------|------|
| 支付牌照 | 决定能否合法运营 | 香港 MSO / 新加坡 MAS / 美国 MSB |
| 跨境结汇 | 决定能否将资金转回中国 | 接入 PingPong / Airwallex |
| 数据保护 | 决定能否服务欧盟用户 | GDPR 合规改造 |
| 反洗钱 | 决定能否避免被处罚 | KYC + AML 流程 |

### 8.2 推荐架构（合规友好）

```
方案 A：Stripe Connect Platform 模式（最快上线，合规风险低）
  - 你作为 Platform，商户作为 Connected Account
  - Stripe 持牌、Stripe 出资金、Stripe 做 KYC
  - 你只赚 Platform Fee（手续费分成）
  - 不需要自己持牌

方案 B：自有牌照模式（长期，高门槛）
  - 在香港/新加坡注册 + 申请牌照
  - 自己持有商户资金（备付金账户）
  - 独立做 KYC/AML/PCI DSS
  - 成本高、周期长（6-12 个月）

方案 C：混合模式（推荐）
  - 短期：Stripe Connect 模式快速验证业务
  - 长期：申请自有牌照
```
